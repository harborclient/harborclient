# HarborClient Visual Brand Guide

## The Developer’s API Workbench

HarborClient is a desktop application for developers who inspect, test, and debug HTTP requests.

Every visual must make that clear immediately.

A viewer should understand within one second that HarborClient is:

- developer software;
- an API client;
- used on a computer;
- part of a real software-development workflow.

HarborClient may borrow the confidence, precision, and craftsmanship of professional instrumentation.

It must not look like marine hardware.

---

# Primary Visual Rule

## Show software first. Use instrumentation only as influence.

The central subject of a HarborClient image should usually be one or more of:

- the HarborClient desktop application;
- an API request or response;
- a developer workstation;
- a terminal;
- a code editor;
- Git;
- JSON;
- logs;
- localhost;
- headers, cookies, authentication, or HTTP status codes;
- a recognizable software-debugging workflow.

Professional instruments may influence:

- materials;
- spacing;
- typography;
- color;
- interface discipline;
- lighting;
- perceived build quality.

They should not determine the literal setting or object being depicted.

### Correct interpretation

HarborClient should feel as dependable and carefully designed as a premium professional instrument.

### Incorrect interpretation

HarborClient should look like software installed inside a radar console, ship bridge, sonar unit, cockpit panel, or piece of marine equipment.

---

# Product Recognition Is Mandatory

Every featured image must contain at least two unmistakable software cues.

Choose from:

- a desktop application window;
- a request method such as `GET`, `POST`, `PUT`, or `DELETE`;
- an HTTP or localhost URL;
- request and response panels;
- JSON or source code;
- headers, cookies, query parameters, or authentication fields;
- terminal output;
- a code editor;
- Git branches or diffs;
- logs or stack traces;
- a visible mouse pointer, keyboard, laptop, or desktop monitor;
- recognizable desktop-window controls, tabs, sidebars, and panels.

At least one cue should be prominent enough to remain readable in a small thumbnail.

A dark rectangular screen by itself is not enough. It must clearly look like developer software rather than embedded hardware.

---

# Visual Priority

Use this hierarchy for featured images:

1. **Article concept or developer problem**
2. **HarborClient or recognizable API-client software**
3. **Real developer-workflow context**
4. **Brand styling**
5. **Subtle instrumentation influence**
6. **Optional maritime recognition detail**

The first three levels are required.

The final two should never overpower them.

## Recommended visual balance

As a general composition guide:

- 50–70%: HarborClient, software UI, code, or article-specific developer concept;
- 20–40%: workstation, terminal, editor, Git, logs, or human developer context;
- 0–10%: subtle instrumentation or maritime-inspired details.

Do not devote most of the frame to a ship bridge, navigation console, ocean view, physical control panel, or industrial enclosure.

---

# Maritime Influence

HarborClient’s name and identity may support restrained maritime references.

These references are mnemonic, not literal product claims.

## Appropriate uses

- a small lighthouse logo or seal;
- a faint navigation grid behind software content;
- subtle coordinate markings;
- a restrained chart-line pattern;
- a small compass-like alignment detail;
- calm navy, steel blue, and telemetry cyan;
- wording such as visibility, signal, clarity, navigation, or bearing when relevant;
- precise panel spacing inspired by well-made instruments.

## Inappropriate uses

Do not make these the primary subject:

- ship bridges;
- boat dashboards;
- radar consoles;
- sonar displays;
- chartplotters;
- ocean navigation screens;
- marine electronics;
- helm controls;
- physical gauges;
- cables plugged into industrial sockets;
- rows of knobs and hardware buttons;
- ships, boats, or ocean scenery;
- nautical maps presented as product data;
- cockpit or military-command environments.

Do not depict HarborClient as embedded software running inside marine hardware.

Do not turn API concepts into literal marine equipment.

For example:

- “request logs” should not become a ship-tracking display;
- “script hooks” should not become physical plugs or cables;
- “chat pointers” should not appear inside a marine console;
- “request routing” should not become a nautical route across an ocean map;
- “monitoring” should not default to radar;
- “navigation” should not automatically mean a ship bridge.

A maritime environment is permitted only when the article itself is genuinely about maritime technology. It should not be used as a general HarborClient brand backdrop.

- part of an existing workflow;

# Visual Metaphor Rules

Visual metaphors should clarify the software concept, not replace it.

## Strong metaphors

- a workbench for a developer workflow;
- an inspection lens over headers or JSON;
- a blueprint layered behind an API request;
- expected-versus-actual annotations;
- a signal trace representing latency;
- a diagnostic timeline;
- a request moving through middleware;
- stacked layers representing an HTTP exchange;
- an engineering notebook beside the application;
- a carefully organized set of software tools.

## Weak or misleading metaphors

- API requests represented only as ships;
- endpoints represented only as ports;
- hooks represented as physical connectors;
- logs represented as nautical charts;
- requests represented as ocean routes;
- debugging represented only as radar;
- errors represented as storms at sea;
- HarborClient represented as ship equipment.

Metaphor should support comprehension after the image is already recognizable as developer software.

# Featured Image Requirements

Blog featured images must communicate three things:

1. the subject of the article;
2. that HarborClient is software;
3. that the article is intended for developers.

## Default composition

Use a 16:9 layout suitable for WordPress, social sharing, and mobile thumbnails.

Prefer:

- one dominant visual idea;
- one short headline;
- a clear focal point;
- generous negative space;
- strong contrast;
- readable software cues;
- a visible HarborClient identity;
- realistic or premium technical execution.

Avoid:

- dense dashboards covering the whole frame;
- tiny unreadable labels;
- multiple competing concepts;
- feature-list text;
- random decorative gauges;
- fake technical complexity;
- a full-screen hardware control panel;
- making the image resemble an advertisement for industrial equipment.

## Headline

Use one headline, usually three to six words.

Examples:

- Inspect Every Request
- Debug Script Hooks
- Follow The Request
- Understand Request Logs
- See What Actually Happened
- Trace The Full Exchange
- Control The Debugging Loop
- The HTTP Workbench

The headline should describe the developer benefit or article topic.

Do not use nautical puns unless the article itself calls for one.

# HarborClient UI

The application UI should feel:

- desktop-native;
- calm;
- structured;
- readable;
- precise;
- premium;
- practical;
- familiar to developers.

Use recognizable software conventions:

- title bar;
- application frame;
- tabs;
- sidebar;
- request URL field;
- HTTP method selector;
- request and response panels;
- syntax-highlighted JSON;
- headers or parameters;
- status and timing information.

Avoid:

- futuristic holograms;
- floating transparent interfaces;
- interfaces physically built into metal consoles;
- oversized hardware bezels;
- knobs controlling the software;
- fictional marine navigation modes;
- radar or sonar controls;
- fake panels unrelated to API development.

Stylized UI is acceptable, but it must remain believable as a desktop API client.

Whenever accurate product screenshots are available, prefer them over invented UI.

# Developer Environments

## Preferred: Developer Workbench

This is the default HarborClient environment.

Examples:

- HarborClient open beside a terminal and editor;
- a failing request alongside backend logs;
- a Git diff beside a changed API request;
- a laptop or desktop monitor showing HarborClient;
- a developer inspecting JSON or headers;
- code, notes, and a real debugging session;
- a clean desk with keyboard, monitor, notebook, and coffee;
- multiple software windows arranged for debugging.

## Preferred: Engineering Workspace

An engineering influence may appear around the software.

Examples:

- notebook annotations;
- technical drawings;
- calipers or measurement tools used as secondary props;
- an oscilloscope-like trace representing request timing;
- blueprint grids behind a desktop application;
- precise materials and lighting.

The computer and software must remain the primary subject.

## Use Sparingly: Control Room

A modern software operations room may work when relevant.

It should show:

- developers;
- desktop monitors;
- logs;
- telemetry;
- application dashboards;
- software diagnostics.

It should not resemble a ship bridge, aircraft cockpit, weapons system, or industrial machinery console.

## Do Not Use by Default: Marine Environment

Do not use:

- vessel interiors;
- ocean views;
- ship windows;
- bridge consoles;
- marine electronics showrooms;
- nautical control rooms;
- helm stations.

These settings create the wrong product-category signal.

# Materials and Physical Styling

Material references should affect finish and mood, not turn the product into hardware.

Appropriate material inspiration:

- matte black;
- dark anodized aluminum;
- brushed metal used sparingly;
- anti-glare glass;
- clean powder-coated surfaces;
- quality keyboards and desk equipment;
- technical notebooks;
- durable professional tools.

Do not wrap the HarborClient UI inside a thick metal enclosure.

Do not add screws, bolts, vents, knobs, power switches, keypads, or physical ports merely to make the product feel “engineered.”

Craftsmanship should come from composition, typography, interface clarity, and attention to detail—not literal machine parts.

# Image-Generation Prompt Structure

When generating a featured image, use this order:

1. Define the article’s developer concept.
2. State that HarborClient is a desktop API-client application.
3. Require a visible software window or developer workstation.
4. Add specific HTTP and development cues.
5. Describe the brand’s calm, engineered visual style.
6. Permit only subtle instrumentation influence.
7. Explicitly prohibit literal marine hardware and settings.
8. Specify a 16:9 composition and mobile-readable headline.

## Prompt template

> Create a premium 16:9 featured image for a developer article about [TOPIC].  
> The primary subject is HarborClient, a desktop API-client application, shown clearly as software on a modern developer workstation.  
> Include recognizable developer cues such as [HTTP METHOD / URL / JSON / TERMINAL / EDITOR / GIT / LOGS].  
> Communicate [ARTICLE IDEA] with one clear visual concept.  
> Use HarborClient’s deep navy, steel blue, white, and restrained cyan accents.  
> The design should feel calm, precise, engineered, and carefully crafted, like a professional developer instrument.  
> Use subtle blueprint or instrumentation-inspired graphic details only as secondary styling.  
> Do not depict a ship bridge, boat, ocean, marine electronics, radar, sonar, chartplotter, cockpit, physical control panel, hardware knobs, industrial plugs, or embedded equipment.  
> The result must immediately read as desktop developer software, not marine hardware.  
> Add the short headline: “[HEADLINE].”  
> Keep the headline readable at mobile-thumbnail size.

## Required negative prompt

Include this block in every featured-image prompt:

> No boats, ships, oceans, ship bridges, helm stations, radar consoles, sonar, chartplotters, nautical maps, marine dashboards, cockpit panels, physical gauges, hardware sockets, glowing cables, control knobs, industrial machinery, military command centers, or embedded-device UI. Do not turn the software feature into a physical machine.

# Failure Conditions

Reject and regenerate an image when any of these are true:

- It could plausibly be an advertisement for marine electronics.
- The HarborClient interface appears built into physical equipment.
- A ship, ocean, bridge console, radar, or sonar display dominates the image.
- The viewer cannot immediately tell that HarborClient is desktop software.
- There is no recognizable HTTP, code, API, or developer-workflow cue.
- Physical controls are more prominent than the software.
- The image communicates “navigation system” before “API client.”
- The article topic has been translated into a literal nautical metaphor.
- The interface looks like an embedded industrial display rather than a desktop app.
- The image is attractive but does not explain the article’s developer subject.

An image that fails one of these conditions is off-brand, even when it looks polished.

---

# Final Review Checklist

Before approving a featured image, answer each question.

## Product clarity

- Is HarborClient unmistakably software?
- Does it look like a desktop API client?
- Is the application or developer workflow a primary subject?
- Could a first-time viewer identify the image as being about software development?

## Article clarity

- Does the image communicate the article topic?
- Are the technical details relevant to that topic?
- Is there one dominant idea?
- Is the headline short and readable?

## Developer relevance

- Is there a visible API, HTTP, code, terminal, editor, Git, JSON, or log cue?
- Does HarborClient fit naturally into a real developer workflow?
- Would an experienced developer recognize the setting?

## Brand character

- Does the image feel precise, calm, dependable, and crafted?
- Is the HarborClient identity visible?
- Are instrumentation influences subtle and stylistic?
- Does the visual communicate confidence rather than spectacle?

## Category safety

- Is marine equipment absent or clearly secondary?
- Is there no confusion between HarborClient and a hardware product?
- Would nobody mistake the image for a Garmin, Furuno, Raymarine, avionics, or industrial-control advertisement?
- Does “developer software” register before “marine” or “navigation”?

If any product-clarity or category-safety answer is “no,” reject the image and generate a new one.

---

# Brand Test

Every visual must pass both tests.

> **Does this look like a serious tool used by skilled developers?**

And:

> **Is it unmistakably a desktop API-client application rather than marine or industrial hardware?**

Both answers must be yes.

HarborClient borrows the discipline of professional instruments.

HarborClient is not the instrument panel.

HarborClient is the developer’s API workbench.
